# AI Usage Report
This document is a mandatory, honest disclosure of how AI was used to build this project, per the assessment's AI Usage Policy.

## AI Tools Used
- **Claude**: Used For BrainStorm, Scaffolding, Templates, With Required Docs.

## How It Was Used
This was built as an interactive, decision-by-decision process, not a single "build the whole app" prompt. For every meaningful technical fork — framework, database, upload strategy, auth strategy, bonus features, validation approach, file storage, dependency manager — Claude presented the available options with their trade-offs and consequences, and a decision was made explicitly before any code was written. Examples of decisions made this way over the course of the build:
- Backend framework: FastAPI
- - Database: MongoDB 
- Upload strategy: ZIP (full folder hierarchy) + drag & drop (flat files) to cover both required options without over-engineering folder-drop support browsers don't reliably expose
- Validation: Pydantic on the FastAPI backend (the real equivalent of Zod, since Zod is TypeScript-only) + Zod on the Next.js frontend forms
- MongoDB access: raw Motor driver
- Auth: JWT access + refresh tokens
- Bonus features: Diff Review + Documentation Generator (chosen over Test Generator, Tech Debt Scanner, Architecture Analysis)
- Python dependency manager: pip + venv over uv/Poetry
- AI provider to build/test against: OpenAI API

## Engineering Decisions
- **Ownership checks at the query level, not after fetching**: every project-scoped endpoint filters by `owner_id`/`project_id` directly in the MongoDB query (e.g. `find_one({"id": project_id, "owner_id": user.id})`), rather than fetching by ID and checking ownership afterward — this means a missing/forbidden resource and a nonexistent one return the same 404, avoiding ID-enumeration leaks.
- **API keys encrypted at rest, masked on every read.** Plaintext keys are never round-tripped back to the client after the initial save.
- **File content is not duplicated into MongoDB.** Only metadata is stored there; content is read from disk on demand. Keeps documents small and avoids two sources of truth.
- **Structured AI output via prompting, not function-calling.** Since the app must support arbitrary OpenAI-compatible endpoints (including local ones like LM Studio, which don't reliably support JSON mode or tool calling), the model is instructed via the system prompt to return a single JSON object, which the backend then parses defensively.
- **Simple keyword retrieval for chat, not embeddings.** The assessment explicitly allows this ("simple context retrieval is acceptable"), and it avoids adding a vector store dependency for a 3-day project.
- **Zod on the frontend + Pydantic on the backend**, not Zod everywhere — Zod cannot run in a Python process, so the closest honest equivalent was used server-side rather than pretending TypeScript tooling applies to a Python backend.
